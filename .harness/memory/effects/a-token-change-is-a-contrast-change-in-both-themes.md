# A token change is a contrast change

`design-system.manifest.json` compiles to **four** outputs: CSS custom properties,
TypeScript constants, React Native styles, and a Tailwind v4 theme.

A token edit therefore changes web and mobile simultaneously — which is the point (they
cannot drift) and the risk (a change reviewed on one surface lands on both).

**Since F-003 this is guarded rather than described.** Gate 9 (`contrast`) is active and
blocking, gate 10 covers the design-system `cvdPairs`, and
`scripts/verify-contrast-proof.mjs` asserts six mutations red with the baseline green in
each.

## The things that catch people

**Both themes are authored, and neither is derived from the other.** ADR-0020 describes dark
as generated by an `L` transform holding `C` and `H` — the manifest does not do that today
(`status.warn` differed in both hue and chroma across the themes until F-003). Either way the
gate checks both independently, because a transform that preserves hue identity does not
preserve contrast ratios.

**A pairing not declared in `pairsWith` is not checked.** The gate checks declared
combinations, not the cartesian product — that is what makes it fast and meaningful. So a
component that uses an undeclared pairing is unverified, and once components exist (F-017)
the gate reports that as a failure rather than passing silently.

**`srgb` is not an input.** It is regenerated from `oklch` by the engine (ADR-0043) and the
gate recomputes and compares. A hand-edited hex fails. Before that rule existed, 37 of 38
opaque tokens carried a hex that did not match their own OKLCh, by up to 6.09 ΔE00.

**A translucent token has no single appearance.** `border`, `border.strong` and
`swatch.hairline` are evaluated over **every** ground they declare, and judged on the worst.
Naming one favourable ground is how a check passes a black hairline that is legible on white
and invisible on a meter track.

## What must happen on a token change

1. `pnpm --filter @irodora/design-tokens generate` — the **five** outputs and the derived
   hexes are regenerated together.

   This note used to say FOUR, and say that the emit tests byte-compare so a skipped
   regenerate is loud. Both halves were nearly true and the gap between them was the defect
   (F-094). `emit.test.ts` compares four artefacts; the fifth is **`apps/mobile/global.css`**,
   the app’s own stylesheet, and it was compared by nothing — hand-editing a hex in it left all
   172 design-tokens tests green. `generate-design-tokens.mjs --check` now runs first in
   `gate:contrast`, so all five are compared and they are compared BEFORE the suites that
   would otherwise agree with stale values.
2. `pnpm test:contrast` — every declared pairing, **both themes**.
3. Check APCA alongside WCAG. A disagreement is usually a real perceptual issue worth looking
   at, even though the gate remains WCAG.
4. If it is a `status.*` token, confirm its `statusPairing` entry still exists. A status
   expressible only as colour must remain unconstructible — and that is a *compile* error,
   not a runtime check.
5. If it is a semantic pair that must stay distinguishable, re-run `pnpm test:cvd`.
6. Check the mobile surface too, not only the web one.

## The token that is easiest to get wrong

`ring` — the focus indicator. It must be 3:1 against **every** surface it can appear on, not
only the page background, and the manifest declares it against all `surface.*` tokens for
that reason.

(This note previously named `border.focus`. No such token has ever existed; it is `ring`.
An effect note that names a token nobody can find is a note nobody acts on.)
