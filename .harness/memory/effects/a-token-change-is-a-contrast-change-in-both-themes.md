# A token change is a contrast change

`design-system.manifest.json` compiles to **four** outputs: CSS custom properties,
TypeScript constants, React Native styles, and a Tailwind v4 theme.

A token edit therefore changes web and mobile simultaneously — which is the point (they
cannot drift) and the risk (a change reviewed on one surface lands on both).

## The two things that catch people

**Dark theme is derived, so a change safe in light is not automatically safe in dark.**
Dark is generated by transforming `L` while preserving `C` and `H`. That preserves hue
identity, which is what makes the brand consistent — but it does not preserve contrast
ratios. The gate checks both themes independently for exactly this reason.

**A pairing not declared in `pairsWith` is not checked.** The gate checks declared
combinations, not the cartesian product — that is what makes it fast and meaningful. So a
component that uses an undeclared pairing is unverified, and the gate reports that as a
failure rather than passing silently.

## What must happen on a token change

1. `pnpm test:contrast` — every declared pairing, **both themes**.
2. Check APCA alongside WCAG. A disagreement is usually a real perceptual issue worth
   looking at, even though the gate remains WCAG.
3. If it is a `status.*` token, confirm its icon pairing still exists. A status expressible
   only as colour must remain unconstructible.
4. If it is a semantic pair that must stay distinguishable, re-run the `cvd` gate against
   `cvdPairs`.
5. Regenerate all four outputs and check the mobile surface, not only the web one.

## The token that is easiest to get wrong

`border.focus`. It must be 3:1 against **every** surface it can appear on — not only the
page background. The manifest declares it against all `surface.*` tokens for that reason.
