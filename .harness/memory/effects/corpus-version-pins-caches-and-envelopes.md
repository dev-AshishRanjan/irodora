# The corpus version pins caches and envelopes

A corpus version appears in two places that make it structural rather than administrative:

- **Every catalog cache key** — CDN, Valkey and client.
- **Every reproducibility envelope** stored with a recommendation (FR-10).

## Why publishing mints a new version instead of invalidating

**Invalidation has a window.** During it, some caches hold the old catalog and some the new,
and a user can see a palette referencing a colour whose values have already changed. A
half-updated catalog is not detectable from inside a single request.

Minting a new version has no window. Old keys stay valid for anything pinned to them; new
requests get the new version. Nothing is ever inconsistent, because nothing is ever
partially replaced.

## Why a published entry is never edited

A recommendation from six months ago stores `envelope.corpus`. Replaying it requires the
values that version held. Editing a published entry makes that replay silently wrong — the
envelope resolves, and it resolves to different data.

Corrections publish a **new version**. The superseded entry is marked, not deleted.

## What must happen on a corpus change

1. `pnpm test:content` — the gate fails on a single incomplete entry. There is no partial
   publication.
2. Derived values regenerated by the engine, never typed
   ([E-001](../../state/effects.json)).
3. A new version label, `YYYY.MM.N`, immutable, checksummed.
4. Checksums verified **at load**, not only at write — a restored backup or a swapped file
   on a self-hosted box never passes through the write path.

## The related risk

**Content is a trust boundary.** Whoever can write here changes what every user is told
without touching code
([threat model §9](../../../docs/architecture/security/threat-model.md)). A checksum
mismatch is a SEV1 with no grace period, because there is no benign explanation for
immutable content differing from its recorded checksum.
