# ADR-0097 — The device carries the policy and runs the gate's own checks

## Status

**Accepted** — F-154. Extends [ADR-0096](0096-a-theme-is-a-hue-on-the-chrome-and-never-touches-the-ground-a-colour-is-judged-against.md),
which decided what a theme may change; this decides where a theme is *verified*.

## Date

2026-09-07

## Context

FR-70's last part asks for a theme seeded by the platform's own colour. A seed like that **cannot
be verified when the manifest is compiled** — it does not exist until the app is running on
somebody's phone.

Every accessibility guarantee this product makes rests on gate 9 and gate 10 having measured a
palette before it ships. A dynamic theme breaks that arrangement at the root: there is no build in
which the values exist.

## The decision

**The device carries the policy and runs the same checking functions CI runs.**

Not a simplified check. Not a heuristic. `checkContrast` and `checkSeparation` — the two functions
gate 9 and gate 10 call — take the palettes as an argument, so the gate passes the real manifest
and the phone passes a derived palette, to the same code.

### Why this is possible here and would not be in most products

`@irodora/color-*` and `@irodora/design-tokens` have **no runtime dependencies, no `node:*`, no
DOM, no `process`**, and produce byte-identical results in Node, the browser and React Native.
That is NFR-3, and it exists so that a colour is the *same* colour everywhere.

It turns out to be the property that makes a **provably accessible** dynamic theme possible. The
guarantee written for correctness is the one that pays for this feature — which is worth recording
because it is not obvious in advance, and because it is a reason not to relax NFR-3 later for
convenience.

### What the device carries

A trimmed manifest — `CheckableManifest` — emitted as a generated module:

| carried | not carried |
| --- | --- |
| the two authored palettes | the six derived families (the device rebuilds them) |
| declared pairings, `usage`, contrast floors | the type scale, motion, elevation |
| CVD pairs and the separation floor | every `role` paragraph |
| the salience rank, the chroma ceiling, the exceptions | — |

**11 KB instead of 36.** The `role` on every token is a paragraph explaining a decision to a
reader, and there is no reader on a phone.

`CheckableManifest` is the *argument type* of the checkers, and a full `Manifest` satisfies it.
That is what stops the two from drifting: there is one set of functions with two callers, rather
than a device implementation that agrees with CI until it does not.

## Three outcomes, and the honest shape of each

**Applied, with corrections.** Chroma is the only lever that preserves lightness and hue, so a
correction is always a chroma reduction — bounded by the manifest's ceiling and by the sRGB gamut
at that token's own lightness. The second is the common one: at L 0.99 the gamut is a sliver, so
nearly every seed is corrected somewhere. **Corrections are reported**, because a theme that
quietly did less than it was asked is a theme nobody can reason about.

**Refused, because the seed is not a colour to take.** A seed below `MINIMUM_SEED_CHROMA` is a
grey with rounding on it, and a hue read off that is noise — a greyscale wallpaper would otherwise
give somebody a theme decided by the last bit of their photograph. A seed outside sRGB or carrying
a non-finite number is refused the same way.

**Refused by the checks — and this path cannot fire today.** Saying so is better than pretending
it might. The derivation preserves lightness exactly and caps chroma at 0.01, so a derived theme
differs from one the gate already passed by less than the check can resolve; a 720-case sweep over
every hue in both modes confirms it.

The check still runs. It is the same code, it costs a few milliseconds, and *"it cannot fail
today"* is a statement about **today's derivation rule** rather than a licence to stop asking. If
ADR-0096's rule is ever loosened — a higher ceiling, a lightness that moves — this is the check
that would catch it, on the device, before the theme is applied.

## Consequences

- **A generated module ships to the app.** It is regenerated by
  `scripts/generate-design-tokens.mjs` like every other target, so a manifest change that is not
  regenerated fails the build.
- **`PairingResult.theme` and `SeparationResult.theme` are `string`**, not `Theme`. A palette
  derived from an accent has no name in a list written at build time, and typing the field as if
  it did would mean the runtime path could not report what it checked.
- **`ThemeValue.name` is a `string` too**, for the same reason, and `ThemeProvider` takes an
  optional `palette` — used only when the person chose the device colour **and** the seed passed.
  There is no third branch where something unchecked reaches a screen.
- **The shareable card takes colours rather than a theme name.** It was only ever using the name
  to look them up, and a runtime palette has none.
- **Nothing can read a platform accent yet.** No dependency in `apps/mobile` surfaces Android's
  dynamic palette, and `PlatformColor` returns an opaque token JS never sees the channels of. The
  port exists and returns `null`; everything downstream is built and swept.

## Alternatives considered

**Check at build time against a grid of possible seeds.** Tempting, and wrong in a way worth
naming: it would verify a set of hues somebody chose in advance and then apply whatever the phone
actually reported. The gap between those two is exactly where an inaccessible theme would live.

**Ship the whole manifest.** 36 KB instead of 11, most of it prose written for people reading the
repository. The trim is not a size optimisation so much as an accurate statement of what a device
needs: the policy, not the reasoning.

**Write a second, smaller checker for the device.** Faster to load and impossible to trust. Two
implementations of an accessibility floor is one implementation and one liability.

**Apply the seed and check afterwards, showing a warning.** This is what most dynamic theming
does. It is not available here: NFR-8 is a floor, and a floor that a person can be shown a warning
about is a preference.
