# ADR-0083 — A PDF report embeds a font its caller supplies, and the parser is proven against a constructed one

## Status

**Accepted** — supersedes the Latin-1-only half of
[ADR-0080](0080-the-pdf-report-is-latin-1-and-refuses-what-it-cannot-draw.md), whose refusal
behaviour it keeps.

## Date

2026-09-02

## Context

[ADR-0080](0080-the-pdf-report-is-latin-1-and-refuses-what-it-cannot-draw.md) chose base-14
Helvetica and WinAnsi, and recorded the cost precisely: **no kanji, no kana, and none of the nine
corpus romaji carrying macrons can appear in a PDF.** A character the writer cannot encode is
refused by name rather than dropped.

For a product whose corpus is Japanese colour names, that is a report which cannot print its own
subject. F-129's criterion 2 is the fix: *"a PDF report can draw kanji, kana and the macron
romaji — an embedded subset, with a ToUnicode map so the text is selectable."*

Two constraints shape every option:

- **`@irodora/export` has no runtime dependencies and no filesystem access.** That is not
  incidental — it is what makes the output diffable, which is
  [ADR-0070](0070-a-shareable-card-is-a-deterministic-document-not-a-bitmap.md)'s whole argument.
  A font library would decide the bytes.
- **The bytes must be deterministic.** No dates, no ids, no compression.

## Decision

**1. The font is a parameter, never a file this package reads.** `toPdf(subject, { font })` takes
TrueType bytes. **With no font, behaviour is exactly as ADR-0080 decided it**: Helvetica,
WinAnsi, and a character it cannot encode refused by name. Every existing caller keeps working
and every one of ADR-0080's refusal tests keeps its meaning.

**2. With a font, the PDF embeds it whole as a `/FontFile2`**, drawn through a `/Type0` font with
`/Encoding /Identity-H` and a `/CIDFontType2` descendant, and carries a **`/ToUnicode` CMap** so
the text is selectable and copyable rather than a picture of itself.

**3. The bytes embedded are the app's existing subset**, generated by
`generate-font-subset.mjs` from the corpus, the catalogue, the lexicon and the taxonomy, and
verified by `verify-font-coverage.mjs` (ADR-0057, E-017). **This package does not subset again.**

**4. A character the supplied font has no glyph for is refused by name**, exactly as an
unencodable one is today. The failure mode does not change; only the set of characters that reach
it does.

**5. The parser's ground truth is a font this repository constructs**, not the shipped one. The
test builds a minimal, valid TrueType file with known metrics and asserts the parser recovers
them.

## Consequences

**Good** — a report can print the names the product is about. The refusal discipline is
unchanged, so nothing is silently lost either way. The package keeps zero dependencies and
byte-determinism. And because the embedded bytes are the *existing* subset, the coverage question
— *does this font contain what the app can render?* — is already answered by a gate that runs
today, rather than by a second pipeline nobody checks.

**Bad** — **the PDF is large.** The subset is roughly 674 KB and there is no compression by
design, so a one-page report becomes a multi-hundred-kilobyte file. That is the price of not
writing a second subsetter, and it is paid on every export.

**A TrueType parser is new surface.** It reads `head`, `maxp`, `hhea`, `hmtx` and `cmap`, and
each is a place to be subtly wrong — a wrong `unitsPerEm` scales every width, a mis-parsed `cmap`
maps a character to the wrong glyph, and **both produce a document that opens and looks
plausible.** Point 5 is the answer to that and is the reason it is a decision rather than a
detail.

**Neutral** — the font arrives as a parameter, so *how the app obtains those bytes* is the app's
problem and can change without touching this package.

## Alternatives considered

| Alternative | Why not |
|---|---|
| **Keep Latin-1 and refuse** (ADR-0080 unchanged) | Honest, tested, and cost nothing to maintain. It also means the flagship export cannot print `藍色`, which is not a limitation this product can keep explaining. |
| **A per-document subsetter** | The right long-term answer: a 20 KB PDF instead of 700 KB. It means rewriting `glyf`, `loca`, `hmtx` and `cmap` and recomputing `checkSumAdjustment` — a second font pipeline with its own failure modes, no gate, and a failure that is a corrupt file rather than a loud error. Named here as the successor rather than attempted inside a feature about export surfaces. |
| **A font library** (`fontkit`, `opentype.js`) | Would do the subsetting properly and immediately. It is a runtime dependency in a package whose no-dependency rule exists so the bytes are ours to diff, and it would decide parts of the output no test here could pin. |
| **Render text to paths** | No font embedding and no encoding questions at all. The text stops being text: not selectable, not searchable, not copyable — which is precisely what criterion 2's ToUnicode clause exists to prevent. |
| **Prove the parser against the shipped subset** | The obvious test, and the weak one: the expected values would have to come from the parser itself, so it would assert that the parser agrees with the parser. A constructed font has known metrics **by construction**, which is [ADR-0081](0081-the-pattern-corpus-is-constructed-so-its-ground-truth-is-exact.md)'s argument in a different domain. |

## Revisit when

**When the report size becomes a complaint, or when a PDF is exported often enough that
hundreds of kilobytes per file matters.** The successor is the per-document subsetter above, and
the parser this ADR adds is the half of it that already exists.

**When a second face is needed** — a Latin face for body text alongside the Japanese one. The
`{ font }` parameter is deliberately singular, and more than one face is a different design.
